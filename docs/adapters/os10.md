# Dell SmartFabric OS10 adapter

The DHCP server of Dell SmartFabric OS10 switches (releases 10.5 and 10.6 researched). Vendor id `os10`.
DHCPv4 only. Manual bindings are written; network pools, ranges and options are read.

> **Status: EXPERIMENTAL, not validated on a real switch.** No OS10 image or switch was available. Everything
> here comes from Dell's published guides (read in part, see "Sources") and from what the fake switch in the
> tests does, and **every fixture and the fake switch are SYNTHETIC**. "Facts and their evidence" numbers every
> CLI fact the adapter relies on (F1, F2, ...) and says which ones were seen in a source and which are inferred.
> Validate on a non-production switch before using it on a production one ("Validation steps for production").
>
> **OS10 has no automatic rollback.** Transaction mode has `commit` and `discard`, and no commit-confirm, no
> timer and no revert of a committed change (F12). Lachesis does not invent one. It checks, reads back, and saves
> only after the read-back matches, and it says so in every plan and every result. If something goes wrong after
> the commit, the change is still live until a person changes it back.

## Transport and authentication

SSH only, through the connection the server's guarded dialer opens, so a switch behind a relay works unchanged.
The endpoint is the management address, `host` or `host:port` (port 22 when absent).

- **Pinned host key.** Set the SHA-256 fingerprint of the switch's SSH host key on the server. With none set,
  Lachesis finishes the key exchange, sends nothing, and fails with the fingerprint the switch presented so you can
  compare it. A key that differs from the pin is a different, never-auto-approved error.
- **Password or key.** A key is tried first. A password is answered to the password method and to the
  **keyboard-interactive** method; some OS10 releases offer only the latter, and a client that only speaks the
  former (such as `sshpass`) is refused (F16). Repeated failed password logins can trigger a login cool-down on the
  switch, so key login is the better choice.
- **A terminal session.** OS10's CLI is not a shell, so Lachesis requests a terminal and a shell and drives the CLI
  one line at a time: it learns the prompt (`name#`, `name(config)#`, `name(conf-dhcp-pool)#`, F19) from the login,
  sends `terminal length 0`, strips the echo and control characters, and answers a `--More--` pager with a
  space if the switch ignores `terminal length 0`. A line that is answered with a question instead of a prompt is
  **not answered**: the session is closed and the operation reports an error. Output, time per line and line
  contents are bounded; a line with `?` or a tab (which a CLI acts on at once) is never sent.
- The password and key are kept only inside the session and never logged or put in an error.

## What it reads

| Capability | How |
|---|---|
| scopes | `show running-configuration`: the `ip dhcp server` block. A pool with a `network` line is a scope; its `range` lines are its pools; `default-router`, `dns-server` and `domain-name` are scope options 3, 6 and 15; `lease` is the lease time. Scopes are disabled unless the block shows `no disable` (F3). |
| reservations | the pools with a `host` and a `hardware-address` line (manual bindings, F6), placed in the network pool that contains the address. The pool name is the reservation's host name. |
| leases | `show ip dhcp binding` (F8), placed in the network pool that contains the address. Expired rows are `expired`. Manual bindings are not in this table (F7). |

The whole configuration passes through memory when the running configuration is read (a way to print only the DHCP
block was not found, F2); only the DHCP block is kept, the rest (users, keys, SNMP) is
dropped as soon as the block has been read and is never logged. A running configuration that is not recognised (no
`hostname` or version line, or an error) is an error, never "no DHCP server". A lease table whose "Total Number
of Entries" differs from the rows read is an error.

Probe reads `show version` (F1) and the running configuration and changes nothing. It warns about: EXPERIMENTAL; no
automatic rollback; an OS10 release other than 10.5 or 10.6; a DHCP server that is disabled or whose state is not
shown; pools it cannot represent; lease times read as UTC; VRFs not modelled.

## What it writes

**Reservations (manual bindings) only: create, update, delete.** A create makes a pool named after the host name
with a `host` address and a `hardware-address`. An update removes and re-creates the pool in the same transaction
(an in-place change of the address or MAC was not found documented, F20). A delete removes the pool.

The sequence of one write, in one terminal session:

1. Read the running configuration and plan against it: collisions (pool name, address, MAC), drift since the plan,
   the address must lie in the scope. Nothing is sent when the wanted state is already there (reported unconfirmed:
   it was observed in the running configuration, the startup configuration was not checked).
2. `configure terminal`, `start transaction`.
3. `show diff candidate-configuration running-configuration` must print **nothing**. The candidate configuration is
   shared by every session and a `commit` applies all of it (F12); if it is not empty Lachesis stages nothing, changes
   nothing and answers *busy* with the instruction to inspect it on the switch. This also stops a second change after
   an earlier one was cut off half way.
4. Stage the lines (`ip dhcp server`, `pool NAME`, `host A.B.C.D`, `hardware-address MAC`, `exit`). A line that
   prints anything is a rejection: Lachesis sends `discard` (nothing was committed, so that undo is certain) and
   reports the change as rejected.
5. `show diff ...` must now print something; then `commit`.
6. `end`, then read the running configuration back and compare **the whole DHCP block** with the expected one. A
   difference anywhere (another session, a partial commit) is caught.
7. Only if it matches: `write memory`. If that prints an error, asks a question or the session is lost, the result is
   unconfirmed: live, matching, but not saved.

The result is confirmed only when the read-back matches and `write memory` reported no error. The startup
configuration itself is not read back, and the result says so.

**There is no automatic rollback and Lachesis does not undo a committed change.** The only undo it performs is
`discard` of staged lines that were never committed. After a commit:

- read-back matches: saved (above);
- read-back is unchanged (the commit was refused or silently discarded): reported as not applied, nothing saved;
- read-back matches neither the old nor the expected state (a partial commit or a concurrent change): reported
  unconfirmed, nothing saved, nothing undone, because Lachesis cannot be sure what an undo would hit. Because nothing
  was saved, a reload of the switch discards the unsaved change; otherwise change it back on the switch;
- the connection is lost: if a new terminal can be opened the read-back decides as above, if not the result is
  unconfirmed with the state unknown; the commit is never retried.

Every plan and every result carries the no-rollback warning.

## What it will not do

It refuses these clearly, before sending anything: pool (range) writes, option writes, lease release, failover
actions; a reservation with a client id, a description or options of its own; IPv6; a host name that is not a
valid pool name (a letter, then letters, digits, hyphen or underscore, at most 32, no dots, F5); an address outside
the scope or in another network pool; replacing or removing a binding that carries settings Lachesis does not model
(they would be lost); a write when no network pool exists (a manual binding needs one, F6); a write while the
candidate configuration is not empty. It does not check that an interface matches a pool or restart the DHCP service
(F10, F11): do that on the switch. It does not read VRF settings (F17).

## Minimum device configuration

```
username lachesis password <set a strong password> role netadmin
! key login, preferred: install the public key for the account (the form used on 10.x is
!   username lachesis sshkey filename <file>; check your release)

ip dhcp server
 no disable
 pool lan1
  network 192.0.2.0/24
  default-router 192.0.2.1
  range 192.0.2.100 192.0.2.199

interface vlan 10
 ip address 192.0.2.1/24
```

The switch must have an interface in each network pool's subnet, or the server does not start (F10). SSH must be
reachable from the machine that runs Lachesis (or from the relay).

## Least privilege

OS10 has a few built-in roles (sysadmin, secadmin, netadmin, netoperator) and, as far as the sources read here say,
no custom roles (F21, not confirmed). Use two accounts:

- **Read only** (scopes, reservations, leases): `netoperator`, if it can run `show version`, `show running-configuration`
  and `show ip dhcp binding` on your release. Check this; if it cannot, use `netadmin`.
- **Writes**: `netadmin`. It can reconfigure the whole switch, so keep the account dedicated, key-only if possible, and
  restrict SSH to the management network. Never use `sysadmin` and never reuse a personal login.

Register the switch once per account if you want reads and writes separated.

## Validation steps for production

Do these on a non-production switch first, then once on production before trusting writes:

1. Register the switch with the read-only account. Probe: it must say the release, a DHCP server state and the
   EXPERIMENTAL and no-rollback warnings. Compare the scopes, reservations and leases Lachesis lists with
   `show running-configuration` and `show ip dhcp binding` on the switch, row by row. Any pool or binding that is
   missing or misread is a parsing fact (F2, F4, F6, F8) that needs correcting.
2. Check the lease time zone: compare a lease's expiry with the switch's clock (F8).
3. Register the writing account. Make sure nobody has a transaction open: on the switch,
   `start transaction` then `show diff candidate-configuration running-configuration` must be empty; leave with
   `discard` and `end`.
4. Plan a **create** of one reservation for an unused address in a pool. Check the plan shows the no-rollback
   warning. Apply it, then on the switch check `show running-configuration` (the pool with the right `host` and
   `hardware-address`), `show diff candidate-configuration running-configuration` (empty), and that the startup
   configuration holds it (`show startup-configuration` or compare `copy` output). Then **update** and **delete** it.
5. Cause a refusal on purpose: create a reservation whose name already exists; it must be refused before
   configuration mode is entered. Leave a transaction open from a second CLI session and plan a change: it must be
   refused as busy, and nothing may change.
6. Check a client that holds a lease picks up a new reservation after the lease ends, and that the interface/pool
   rule (F10) holds for the pool.
7. Only then enable writes for the production account, and keep a copy of the startup configuration: there is no
   automatic rollback.
